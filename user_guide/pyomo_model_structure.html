Pyomo Model Blocks and Input Provenance

This reference describes the investment/dispatch model returned by initialize_model: where components live, their Pyomo types, and how CSV inputs become mathematical quantities. It complements the copperplate formulation, zonal formulation, and interactive inspection guide. The separate outage models built by evaluate_resiliency are described in the resiliency formulation, not inventoried here.

Composition and conventions

A host is the copperplate model or a zonal model.area[a]. Builders reuse the same technology blocks on either host. The diagrams use nested containers to show ownership. Containers named model, area[a], or a technology are actual model/Block boundaries. Inner Parameters, Variables, Expressions, and Constraints containers are visual field groups, not additional Pyomo Blocks. Invisible layout links only arrange the boxes; they do not represent data flow.

Comma-separated names in a box are sibling Blocks, not an extra container. The zonal diagram shows two representative areas; area[a] is repeated for every member of model.A. The detailed field-group diagrams below apply to each area’s technology Blocks as well as the copperplate host. Block existence does not imply active technology. All ten technology blocks are created even for empty fleets. reserves is created only when its formulation is enabled. resiliency is an optional copperplate placeholder; the legacy fields and constraints are on the host. Zonal mode rejects legacy resilience constraints and enabled external imports/exports.

Read the tables as follows:

  • Param is input or derived fixed data; Var is a solver decision; Expression is an attached symbolic formula, not an independent decision. Set supplies indices. Entry denotes an entry in a property-matrix Param, not another component.

  • Names are local to the block: generation[h,k] in the thermal table means model.thermal.generation[h,k] or model.area[a].thermal.generation[h,k].

  • h indexes one-hour steps, \(k\) a plant, \(j\) storage, \(b\) a hydro period, \(a\) an area, and \(\ell\) a line. Zonal symbols add the area index to local quantities; Python index order need not match mathematical subscript order.

  • scalars.csv: X means the row with Parameter=X, column Value. StorageData.csv: X, j means row X in the first-column property index, technology column j. Other file: column references are column names.

  • CSV loading rounds most numeric technology/profile data to five decimals. Scalars and validated thermal minimum-dispatch fractions retain their validation-specific handling. Parameters retain their tabulated units: the cost formulas, not the CAPEX/FOM Params, apply the factor \(10^3\).

  • Requested n_hours determines the horizon, rounded up to complete 24-hour daily or 730-hour monthly hydro periods. All hourly fields use this effective horizon. Fixed costs are annual USD/year; dispatch costs are USD over modeled hours and are not annualized for a shortened run.

For zonal provenance, area_id in CapSolar.csv, CapWind.csv, and Data_BalancingUnits.csv selects the host. Wide columns such as Load@A1@ or Li-Ion@A1@ are split by area and their tags removed before the same builders run. CF headers identify plants and may be area-tagged; ownership must agree with the capacity table. Thermal minimum-dispatch headers are globally unique plant IDs, not area-tagged. Areas without a profile/technology receive empty fleets or zero profiles; absent budget hydro also receives zero lower/upper bounds. See the exact base schemas and zonal slicing rules.

Input provenance or definition

h

Set

\(\mathcal H\), one-based hours

Effective initialize_model(..., n_hours=...) horizon, not a CSV scalar.

r

Param

\(r\), dimensionless discount rate

scalars.csv: r.

FCR_VRE

Param

\(a^{vre}\), inverse years

Derived \(\operatorname{CRF}(r,l^{vre})\) from scalars.csv: r and l_vre.

GenMix_Target

Param

\(\tau\), clean-generation fraction

scalars.csv: GenMix_Target; mutable. Area copies exist, but zonal clean share uses the root Param.

EUE_max

Param

\(EUE^{max}\), MWh

scalars.csv: EUE_max; mutable, declared even without legacy resilience constraints.

net_load[h]

Expression

\(n_h\), MW

Gross demand minus fixed nuclear/other renewables and scheduled hydro, minus pv/wind hourly availability (generation plus curtailment). No direct input column.

LoadShed[h]

Var

\(L_h\ge0\), MW

Only with legacy resilience constraints; no CSV value initializes the decision.

aux_imp_exp_binary_variable[h]

Var

\(V_h\in\{0,1\}\)

Only with net-load-coupled external trade; not used for zonal line flows.

The root objective Obj minimizes fixed investment/O&M plus thermal fuel/VOM, storage discharge VOM, signed technology curtailment costs, and, in copperplate mode, imports expenditure minus exports revenue. Zonal Obj sums local costs once across areas; transmission investment cost is currently zero. Area hosts have no separate objective or clean-share constraint. SupplyBalance and storage SOCBalance live on each host, even though most other operating constraints live inside technology blocks.

PV and wind

Both blocks have the same schema. Use CapSolar.csv/CFSolar.csv for pv and CapWind.csv/CFWind.csv for wind. In the table, Cap*.csv and CF*.csv mean these exact corresponding files. Generic \(P_k,F_k,G_h,C_h\) stand for the formulation’s PV or wind quantities: \(k=p\) or \(w\), \(F_k=F^{pv}_p\) or \(F^{wind}_w\), \(G_h=G^{pv}_h\) or \(G^{wind}_h\), and \(C_h=C^{pv}_h\) or \(C^{wind}_h\). Likewise \(\kappa_k,\phi_k,t_k\) denote \(\kappa^{pv}_p,\phi^{pv}_p,\kappa^{tc,pv}_p\) or their wind counterparts, and \(CF_{kh}\) denotes \(\sigma_{ph}\) or \(\zeta_{wh}\). The formulation’s cost symbols use converted per-MW units; the table therefore maps raw per-kW Params to these symbols divided by \(10^3\). Derived capacity/energy/cost totals and annualization factors use descriptive aliases when the mathematical formulation does not name them individually.

Inspecting actual ownership

This example lists only directly owned fields, avoiding accidental duplicate counts when traversing nested blocks. It needs no solver.

from pathlib import Path

import pyomo.environ as pyo

from sdom import initialize_model, load_data

data = load_data(str(Path("Data") / "zonal_test"))
model = initialize_model(data, n_hours=24)

for block in [model, *model.component_data_objects(pyo.Block, descend_into=True)]:
    print(block.name)
    for kind in (pyo.Set, pyo.RangeSet, pyo.Param, pyo.Var, pyo.Expression):
        for component in block.component_objects(kind, descend_into=False):
            print(f"  {kind.__name__}: {component.local_name}")

The construction entry point is optimization_main.initialize_model; initializations builds shared sets and host Params; models/formulations_*.py populate technology/network fields; models/models_utils.py supplies profile and common cost/budget helpers. The model-builder API links those source-backed functions.
